Caddy 从零上手：自动 HTTPS 的 Web 服务器

如果你只是想让一个网页、一个 API、一个自建服务能从浏览器打开，那 Caddy 大概是目前最省事的选择：一个可执行文件、一个十来行的配置文件、证书自动申请自动续期，不用再折腾 certbot、不用记 nginx 的括号和分号。

这篇写给完全没用过 Caddy 的人。所有配置片段都用 Caddy v2.11.9 实际跑过 caddy validate，命令也实际执行验证过，可以放心抄。

一、Caddy 和 Nginx 差在哪

对比项 Nginx Caddy
HTTPS 证书 自己装 certbot，写 cron 续期，改配置 reload 自动申请、自动续期、自动跳转，全自动
配置文件 分号、大括号、location 嵌套，缩进错了就报错 十来行、按行读就懂的 Caddyfile
静态文件 location / { root ... } file_server 一行
反向代理 proxy_pass + 一堆 proxy_set_header reverse_proxy 127.0.0.1:3000 一行
HTTP/3 要单独编译 默认开启
安装 装包 / 编译 / 各种依赖 单文件，解压就能跑

代价也要说清楚：Caddy 的内存占用比 nginx 略高（几十 MB 对十几 MB），生态和第三方模块没 nginx 多，用 Go 写的、要扩展得用 xcaddy 重新编译。对个人站、小项目、自建服务来说，这些都不重要，省下来的运维时间更重要。

二、先搞懂三件事，不然会一直懵

新手卡住，九成不是 Caddy 的问题，是这三件事没理清：

1. 域名 → DNS → IP
你在域名商那里把 example.com 的 A 记录指向服务器公网 IP，浏览器才能找到这台机器。DNS 没生效（或者指错了），Caddy 申请证书一定失败，它只能通过”访问这个域名”来证明你是这台机器的管理者。

2. 80 和 443 两个端口

  • 80：HTTP，明文。
  • 443：HTTPS，加密。
  • Caddy 默认会同时监听这两个端口：443 上跑你的站，80 上只做一件事——把用户 301 跳到 443。

所以服务器防火墙、云厂商安全组必须放行 80 和 443（还有 443/udp，那是 HTTP/3）。这一条没做，症状就是”证书申请一直卡着”，翻到本篇第十三节有排错清单。

3. 反向代理是什么
你的应用（Node/Python/Go 写的）通常监听在 127.0.0.1:3000 这种高位端口上，外网访问不到。反向代理就是这个”门房”：外面访问 https://example.com，门房收到后转给里面的 3000 端口，再把结果原样返回。这样 HTTPS、证书、压缩、限流都由门房统一处理，应用本身不用管。

Caddy 干的就是这个门房，而且它是自动配好 HTTPS 的门房。

三、装 Caddy

Windows

到 caddyserver.com/download 下 windows amd64 的 zip（也可以 choco install caddy），解压得到一个 caddy.exe。

Windows 上 Caddy 的数据目录是 %AppData%\Caddy（证书、密钥、自动保存的配置都在这里），无需手动创建。

Debian / Ubuntu（推荐用官方源，能用 systemd 托管）

装完会自动注册成开机自启的服务，配置文件在 /etc/caddy/Caddyfile，日志用 journalctl -u caddy -f 看。

Docker

三点必须照做，否则证书每次重启都要重新申请（很快会撞上 Let’s Encrypt 的限流）：

  • /data 必须挂卷：证书就存在这里；
  • /config 建议挂卷：Caddy 自动保存的配置；
  • 443/udp 要映射，不然 HTTP/3 不生效（不影响 HTTP/2，只是少了点速度）。

五、自动 HTTPS：它到底做了什么

把上面的 :8080 换成一个真实域名：

重新 caddy reload，Caddy 会自己完成这些事：

  1. 向 Let’s Encrypt（或 ZeroSSL，会自动挑选可用的 CA）申请 example.com 的证书；
  2. 通过”访问一个特定 URL”来证明域名确实指向这台机器（HTTP-01 挑战：它在 80 端口临时放一个验证文件，CA 从公网来取）；
  3. 拿到证书后存在本地数据目录，443 端口开始提供 HTTPS；
  4. 把 80 端口的请求 301 跳到 443；
  5. 到期前约 30 天自动续期，续期失败会重试，你什么都不用做。

证书位置：

系统 路径
Linux（root 运行） /root/.local/share/caddy
Linux（普通用户） ~/.local/share/caddy
Docker 容器内 /data（挂卷就到宿主机了）
Windows %AppData%\Caddy

一个新域名从 0 到能访问，通常十几秒。 但如果 DNS 还没生效、或者 80/443 没放行，就会卡住——这就是新手最容易踩的坑，见第十三节。

十二、内网服务放出来（自建服务标配）

你家里/服务器上跑了一堆面板：PVE 8006、路由器后台、NAS、Jellyfin……它们都是 HTTP、都不带证书。用 Caddy 加一层：

要点：

  • tls internal：内网名字拿不到公网证书，用本地 CA 签；
  • tls_insecure_skip_verify：上游自己用的是自签证书（比如 PVE 默认那样），不校验它，否则握手失败；
  • 记得 caddy trust 一次，让电脑和手机信任本地 CA，否则浏览器还是提示不安全。

如果你有域名并且解析到了公网 IP，那这些服务可以直接用子域名（pve.example.com）走自动 HTTPS，比内网自签省事得多——只是要把服务暴露到公网，注意设密码和访问控制。

十三、新手必踩的坑（对照排查）

现象 原因 解决
启动报 permission denied 绑 80/443 非 root 用户不能绑 1-1024 端口 用 root / sudo 跑，或 sudo setcap cap_net_bind_service=+ep /usr/bin/caddy
证书申请一直卡住，日志里 challenge failed 80 端口不通：防火墙、云安全组、运营商封 80 放行 80/443；云服务器还得改安全组
同上，但域名是 Cloudflare 橙云 流量经过 CF，Caddy 拿不到真实验证请求 关掉橙云（灰云），或改用 DNS 挑战 / 用 CF 的源站证书
no such host / 域名解析失败 DNS 没生效或 A 记录填错 dig example.com 确认指向服务器 IP，等 TTL
站点能开但显示 502 上游服务没起、端口写错、监听在 127.0.0.1 之外 curl 127.0.0.1:3000 先确认应用活着
浏览器提示 ERR_TOO_MANY_REDIRECTS 应用自己也做了强制 HTTPS 跳转，和 Caddy 互相踢皮球 关掉应用的 HTTPS 跳转，只让 Caddy 管
上传大文件报 413 默认不限，但上游（nginx/PHP/应用）有限制 改上游或应用的请求体上限
Windows 上 caddy run 一闪就退 端口被别的程序占了（IIS、Skype、旧 Caddy 进程） netstat -ano | findstr :443 查占用，换端口或杀进程
改了配置不生效 只改了文件没 reload caddy reload --config Caddyfile，报错会直接打在终端
触发 Let’s Encrypt 限流 反复测试导致重复申请 同一注册域名每周限 50 张、同名证书每周 5 张，等一周或用 --staging 测试

测试期强烈建议：先在本地或子域名上折腾，别拿主域名反复试。真要反复测，把全局选项里的 CA 换成测试环境（acme_ca https://acme-staging-v02.api.letsencrypt.org/directory），它的证书不被信任，但不限流，调通了再换回来。

十四、从 Nginx 迁移：对照着改

目的 Nginx Caddy
静态目录 root /var/www; index index.html; root * /var/www + file_server
反代 proxy_pass http://127.0.0.1:3000; reverse_proxy 127.0.0.1:3000
反代并保留真实 IP proxy_set_header X-Real-IP $remote_addr; 自动
WebSocket proxy_set_header Upgrade $http_upgrade; proxy_set_header Connection "upgrade"; 自动
gzip gzip on; gzip_types ...; encode gzip
跳转 return 301 https://$host$request_uri; redir https://{host}{uri}
路径前缀剥除 location /api/ { proxy_pass http://127.0.0.1:8000/; } handle_path /api/* { reverse_proxy 127.0.0.1:8000 }
单页应用回退 try_files $uri /index.html; try_files {path} /index.html
加响应头 add_header X-Frame-Options DENY; header X-Frame-Options DENY
密码保护 auth_basic + htpasswd 文件 basic_auth { user $2a$... }
访问日志 access_log /var/log/nginx/a.log; log { output file ... }

一句话总结 nginx 用户的迁移体验：把 proxy_set_header 那一堆全删掉、把 location 换 handle、把 root 后面加个 *，剩下的基本一一对应。

十五、日常运维

备份清单只有两样：

  1. Caddyfile（以及 import 进来的片段文件）；
  2. 数据目录里的 pki/ 和 certificates/（Linux ~/.local/share/caddy，Windows %AppData%\Caddy，Docker 的 /data 卷）。

搬服务器时把这两样带过去，证书还能继续用，不用重新申请。

十六、小结

Caddy 的核心价值就一句话：把”申请证书 + 续期 + 配 HTTPS + 反向代理”这一整套运维动作，压成了配置文件里的几行字。

如果这篇文章只让你记三件事：

  1. 有域名就用 域名 { reverse_proxy 127.0.0.1:端口 }，HTTPS 白送；
  2. 没域名（内网/本机）就加 tls internal + caddy trust；
  3. 改完配置永远用 caddy reload，不要重启。

剩下的，查第八节的指令表就够了。
